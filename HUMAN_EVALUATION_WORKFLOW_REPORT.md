# Human Evaluation Workflow Report

## Models And Endpoints

Added dedicated evaluation persistence:

- `evaluation.human_evaluations` stores evaluation-set version, example ID,
  task, model/prompt versions, rubric version, inference configuration, output
  digest, JWT-derived reviewer ID, comments, evidence references, and timestamp.
- `evaluation.human_evaluation_scores` stores the five independent rubric
  dimensions on the required 0–4 scale.

Added authenticated endpoints:

- `GET /api/v1/evaluation/human/examples`
- `GET /api/v1/evaluation/human/examples/{exampleId}`
- `POST /api/v1/evaluation/human/reviews`

Compatibility aliases under `/evaluation/human/**` are also available. The
immutable JSONL evaluation set is read-only; only review records are written.
Duplicate submissions by the same reviewer and example are rejected with a
conflict response.

## Frontend Changes

Added a dedicated **Human Evaluation** workspace separate from Training Review.
It provides:

- held-out queue progress: scored, remaining, and submitted state
- scenario and task metadata
- problem input and retrieved evidence/context
- citations and allowed source IDs
- BASE Qwen output
- provenance, model/prompt metadata, and inference configuration
- task-specific rubric controls for all applicable dimensions
- evidence-reference capture and reviewer comments
- explicit submit action with incomplete-form validation

No scores are generated by the frontend or backend.

## Authorization Result

Human evaluation reads require an existing evaluation/governance authority:
`EVALUATION_READ`, `AI_SAFETY_REVIEW`, `GOVERNMENT_POLICY_REVIEW`,
`AI_GOVERNANCE_REVIEW`, or `AI_ADMIN`.

Score submission requires a review authority and derives `reviewerId` only from
the authenticated JWT principal. No reviewer identity field is accepted from
the request body. Unauthenticated reads and submissions are rejected.
