# Master Technical Debt Register

Purpose: Captures the enterprise repository audit findings that must be resolved before Production Candidate v1.
Why it exists: A single prioritized debt register prevents architecture drift from being hidden across milestone notes, implementation summaries, and local validation logs.
Architecture fit: This document governs remediation across the modular Spring Boot backend, Next.js portals, Python AI services, shared packages, data schema, CI/CD, infrastructure, and `.ceos` engineering operating system.

Related documents: [MASTER_ARCHITECTURE_REPORT.md](MASTER_ARCHITECTURE_REPORT.md), [MASTER_REFACTOR_PLAN.md](MASTER_REFACTOR_PLAN.md), [MASTER_PRODUCTION_CHECKLIST.md](MASTER_PRODUCTION_CHECKLIST.md), `.ceos/constitutions/architecture-constitution.md`, `.ceos/constitutions/security-constitution.md`.

## Executive Summary

The repository is structurally strong for a fast-moving enterprise platform: it has bounded backend modules, Flyway migrations through the research laboratory milestone, local Docker Compose topology, GitHub Actions, documented engineering standards, and tests across all implemented backend domains. The remaining debt is not basic scaffolding debt. It is production-candidate debt: release governance, API consistency, tenant isolation, CI coverage on protected branches, data lifecycle enforcement, AI artifact realism, and operational hardening.

## Debt Acceptance Rules

Debt may remain open only when one of these is true:

1. The risk is explicitly accepted by the Architecture Board and Security Board.
2. The debt is outside the active milestone and has a dated remediation milestone.
3. The debt is a deliberate local-development convenience that is technically prevented from reaching production.

Anti-patterns:

- Treating architecture target-state documentation as implementation evidence.
- Treating local passing tests as proof that GitHub branch protection is adequate.
- Keeping demo seed behavior inside read paths.
- Adding more modules before stabilizing API, tenant, and CI controls.
