# Documentation Standards

## Purpose

This standard defines how engineering documentation must be written and maintained.

## Why

Documentation is the durable memory of the engineering organization. It must reduce ambiguity, not merely satisfy a checklist.

## When

Apply this standard to every CEOS document, architecture document, runbook, API contract, migration note, model card, data card, release review, and incident review.

## How

- Explain purpose, why, when, how, tradeoffs, best practices, anti-patterns, and related documents.
- Link to related policy and implementation documents.
- Use concrete rules rather than aspirational language.
- Keep documents updated with the change they govern.
- Use templates from [Templates](../templates/README.md) for repeatable documents.

## Tradeoffs

Detailed docs take longer to write but reduce repeated debate and prevent institutional knowledge loss.

## Best Practices

- Prefer concise paragraphs with explicit decisions.
- State ownership and approval authority.
- Record exceptions and their expiration conditions.
- Keep examples close to standards.
- Avoid undocumented acronyms.

## Anti-Patterns

- Empty sections without enforceable guidance.
- Vague phrases such as “handle errors appropriately” without criteria.
- Duplicating conflicting standards across directories.
- Documentation that cannot guide implementation.
- Hiding important decisions in chat history.
